论点 01

"You still need humans in the loop. Don't surrender to the machine. We can use the machines, but don't cognitively surrender — because it's so easy to build, the things that stand out are the things that are really well thought through."
「人必须留在回路里。别向机器认知投降。可以使用机器,但不要在认知上投降 —— 因为太容易把东西做出来了,唯一能留住注意力的就是真正深思熟虑过的产品。」
MIRA · 批注
MIRA · 批注:这是与 Vol.007 'Taste as the New Axis' 的隔空对答。Ahmad Awais 把 taste 编码进 Taste-1 是工程视角,Fadell 是产品/创始人视角 —— 警告创始人/PM 不要把 judgment 让渡。两端合起来才是完整图景:taste 既要可工程化(可被 harness 蒸馏),又必须有人在场(decision authority 不外包)。Gaming 立项 RFC 模板下个周期必须加一栏『本立项中,哪些 judgment 不允许由 AI 决定?(unless override by PM)』,作为防止 cognitive surrender 的制度护栏。

论点 02

"Today in the AI world, I can just make a prompt and all of a sudden it gets spit out... You're building on a really crusty foundation. You're getting short-term gain for very very long-term loss. If you're going to build a real company, can't be throwaway."
「在 AI 时代你只要写个 prompt,东西就被吐出来了……你在一个非常脆弱的地基上盖楼。你赚的是短期、亏的是长得多的长期。如果你真的要建一家公司,这种『一次性』模式行不通。」
MIRA · 批注
MIRA · 批注:Fadell 直接引用 Claude 源码泄露事件 —— 资深架构师看到 Anthropic main loop 后『 threw up 』,因为 90-100% AI 写的代码被认为是 brittle、不可分层、不可维护。这是 2026 H1 最强反共识声音之一,与 Vol.006 Anthropic RSI 自陈 80%+ Claude-written code 形成正面对撞。Gaming 立项必须做出选择:核心系统(reward/anti-cheat/economy)走 senior-led 架构 + AI 辅助;边缘工具(运营脚本/dashboards/内部 CRUD)走 AI-first vibe code。这条边界今天必须由 CTO 级别画清楚,不要任凭团队按工具便利度自动滑入 vibe-code 区。

论点 03

"It took three generations of the iPod before it became successful. You got to fail a few times till you find your way... A customer only sees what they see through the lens of marketing."
「iPod 用了整整三代才真正成功。你必须先失败几次,才能找到对的路……用户能看到的一切,都只是 marketing 镜片里的样子。」
MIRA · 批注
MIRA · 批注:'三代法则' 在 AI 产品时代有新含义:大模型 + iteration 极快 → 容易让团队以为可以一次到位,跳过『v1 失败、v2 调整、v3 成立』的自然节奏。Gaming AI 副驾的 12 个月 roadmap 应显式分成 v1(让玩家用上)/ v2(让玩家愿意付费)/ v3(让玩家自发分享),并设置 v1 和 v2 是『允许失败、必须学习』的窗口期。第二句话同样硬核 —— marketing 不是 GTM 后置环节,是 product 的一部分。Gaming AI 玩家工具命名、首屏文案、社区发布角度,应该和 spec 同期 owned 而非交付后由 marketing 加包装。

论点 04

"You need taste makers — the person or the team who is going to make those opinion-based decisions. This is a benevolent dictatorship. Data alone gives you just data — you have to figure out how to get opinion-based decisions to happen."
「你需要『taste maker』—— 那个负责拍板的人或团队。这是一种『仁慈的独裁』。光有数据只会给你数据 —— 你必须想办法让 opinion-based 的决策真的发生。」
MIRA · 批注
MIRA · 批注:这条直击当下 Gaming 决策模式 —— A/B 数据驱动派 vs taste 派的张力。Fadell 不是反数据,是反『把决策外包给数据』。新产品 1.0 没有数据可外包,只能靠 taste maker;有数据之后,数据是用来 sanity check taste,而不是替代 taste。Gaming AI 玩家工具的『定调权』(tone-of-voice / 默认人设 / failure dialog 措辞)必须固定一个 named taste owner,不可委员会化、不可 A/B 化、不可 LLM 自动生成。这位 taste owner 的 KPI 应是『被 AI 提案后否决的比例 ≥30%』 —— 否决率太低意味着已经认知投降。

论点 05

"The end ideal product is a piece of glass that we look at... You still need a screen or something to project on. If you look at Her — the movie — they had glass there for certain things... Hardware is the foundation; software innovation can't get to the next level without next-level hardware."
「最终的理想产品就是一块我们看的玻璃……你始终需要一块屏幕,或者某种你可以投影到的载体。看看《Her》那部电影 —— 关键场景里其实还是有玻璃……硬件是地基;没有下一代硬件,软件创新就推不到下一层。」
MIRA · 批注
MIRA · 批注:Fadell 公开反对 Humane / Friend.com 这类『无屏 ambient 硬件』叙事,主张屏幕是 AI 时代不可绕过的终端。这对 Gaming 战略含义巨大:1) 不要把宝押在 wearable AI 设备上的玩家入口;2) 短视频 + AI 玩家的下一站仍然在『竖屏 + 玻璃』里展开,UI 投入回报率高于硬件投入;3) 与 Snap 创始人本周观点一致 —— '软件公司唯一存活路径是配硬件',Gaming 直播/创作者侧的硬件配套(机位/补光/teleprompter)可能是下一波低估的 leverage 点。

TIKTOK GAMING · TAKE-HOME

  1. 本周内发出『Cognitive Surrender 防护清单』给 Gaming 核心 PM 团队:列出 3-5 个绝不允许 AI 决定的 judgment(玩家承诺、安全/合规、定价、品牌口吻、付费墙位置),作为团队默认 norm,RFC 模板加入该字段。
  2. 做 fast-vs-slow 代码边界 RFC:核心系统(reward/anti-cheat/economy/payment)= senior-architected + AI 辅助;运营工具(dashboards/内部 CRUD/data 探索)= AI-first vibe code;每条 vibe-coded 服务必须挂 tech-debt 计时器,超过 90 天自动进入 senior review queue。
  3. 为 Gaming AI 副驾 12 个月 roadmap 显式标注『三代法则』节点:v1=可用、v2=可付费、v3=可分享;v1 和 v2 不背 ROI KPI 而背 learning KPI(每代必须沉淀 ≥10 条 user-verified insight);避免被『AI 一次到位』错觉误导。
  4. Gaming AI 玩家工具任命一位 named taste owner(不是委员会),其 KPI 包含『被 AI 提案后否决的比例 ≥30%』,low 否决率视为认知投降信号;每月在产品 review 上 30 分钟公开『本月否决的 5 个 AI 提案及理由』。
  5. 停止评估 wearable / no-screen 玩家硬件,把硬件 R&D 预算挪到创作者/主播侧的『屏幕周边』(机位智能跟拍 / 补光 / AI teleprompter / 实时弹幕投屏),与 Snap 创始人本周『软件公司唯一存活路径配硬件』观点一致。

论点 01

"If you review every single line of code, you become the bottleneck. So I don't review this first pass code from the agent. Eventually I got to a point where I find myself never catching anything the agents don't catch."
「如果你逐行审 agent 写的代码,你自己就成了瓶颈。所以我根本不看第一遍 diff。最后我发现 agent 漏掉的东西我自己也漏。」
MIRA · 批注
MIRA · 批注:Kun 的 'no mistakes' 工具关键是用 fresh context window 让另一个 agent 审 PR,不是同一个 session 里『agent 自我审查』(因为自我审查会被先前 reasoning 带偏)。Gaming 工程已有 LLM-as-judge 实验,但很多是 same-session 自审,需要 60 天内升级为『独立 reviewer agent + 独立 prompt + 独立工具链』。预期效果:bug 召回率与 senior reviewer 同等水平,但延迟降到 PR 提交 5 分钟内。

论点 02

"How much time we invest in the planning phase actually affects this a lot. If I spend a lot of time crafting a very detailed plan, then I can let the agents go for longer."
「在规划阶段投入多少时间,会显著影响 agent 自主跑多长。我把 plan 打磨得越细,agent 能独立跑的窗口就越长。」
MIRA · 批注
MIRA · 批注:这是 Vol.005-007 反复出现的『environment / harness / spec / loop』四件套在个人维度的具体表达。给 Gaming 工程团队的具体处方:把 spec 写成『measurable goal + 验收 checklist + 自动 E2E test 脚本骨架』三段式,允许 agent 在该 spec 下连续跑 ≥45 分钟无人工介入。新 KPI:本周内可以让 agent 独立跑的最长 wallclock 窗口(MUW, max unattended window)。MUW 是个人 agent 工程能力最诚实的指标,比 PR 数更可信。

论点 03

"I use a visual editor to do the planning — Lavish. The HTML as an artifact can be a lot richer in terms of supporting collaboration between human and agent. It's not going to be a long wall of text I have to read through."
「我用一个自己写的可视化编辑器 Lavish 做规划。HTML 作为产物比 markdown 长文更适合人机协作 —— 我不用通读一堵文字墙。」
MIRA · 批注
MIRA · 批注:Vol.007 已经记下了『HTML > markdown 作为 agent artifact』的趋势,Kun 这里给出第二个独立印证。但更深的信号是:Kun 自己造了 Lavish。下个 12 个月 senior IC 的标志性能力,是『识别工作流中的 friction → 直接造一个内部工具消除它』,而不是『提工单等平台解决』。Gaming 工程组内部应公开鼓励 senior 写 100-行级别『自用 micro-tool』,每月在 dev share 上 demo,优秀者集中转成团队基础设施,但不强制 productionize(避免 senior 自用工具走向重型化)。

论点 04

"I typically have at least five different sessions actively running. On average, there's like 20 to 30 agents running. Most of the time it's like 20 to 40 PRs every day. Our workflows and how our teams work were built at a time when we spend most of our time coding. But when you start to write 10 times more PRs, we are not ready for that to really scale up."
「我同时至少跑 5 个 session,平均 20-30 个 agent 在跑,大多数日子产出 20-40 个 PR。但我们今天的研发流程是按『大多数时间在写代码』时代搭建的;一旦 PR 量翻 10 倍,这套流程压根撑不住。」
MIRA · 批注
MIRA · 批注:这是 Gaming 中台研发组 60 天必须解决的『agent-era PR review bottleneck』问题。当前 PR review 流程基于人均 3-5 PR/天的假设,而 senior IC 在 agent 加持下可能直接跳到 30-50 PR/天。要做的事:1)PR 自动分级(高风险=人工 review;中=fresh-context agent review + 人工抽检 20%;低=纯 agent review + 全量 E2E 自动测试通过即可 merge);2)reviewer rotation 频率从每周改每天(避免单人被 PR 雨淹);3)code review 工时纳入正式 KPI 而不只是 'good citizen' 行为。

论点 05

"The test phase will actually present some evidences of the change actually working — it will paste screenshots or sometimes a video to capture this thing is actually working, so it's easier for me to review."
「测试阶段会主动呈现『改动真的能工作』的证据 —— 会自动贴截图、有时是视频,这样我审起来很容易。」
MIRA · 批注
MIRA · 批注:这是把 'evidence-first PR' 从理念变成默认 norm。Gaming 客户端/H5 改动尤其适合 —— 每个 UI/玩家流程 PR 都要附 30 秒 Playwright 录制的 GIF + 与上一版本的 visual diff。具体落地:LiveOps 工具链 60 天内升级 PR template,强制要求『证据卡片』(screenshot / video / metric delta);无证据卡片的 PR CI 自动 block。

TIKTOK GAMING · TAKE-HOME

  1. Gaming 中台研发引入『MUW 季度指标』:每位 senior IC 报告自己『可以让 agent 独立跑的最长 wallclock 窗口』,从分钟级 → 小时级是 H2 目标;不达 30 分钟的工程师配 senior IC 1:1 coaching,补 spec 写作能力。
  2. 搭建『独立 reviewer agent』服务(fresh context + 独立 prompt + 独立 MCP 工具);所有 PR 在分配给人之前先过 reviewer agent,review 报告 1 分钟内返回作者。
  3. PR 分级 RFC:高风险(reward/anti-cheat/payment/数据库 schema)→ 人工 review 必须;中风险 → agent review + 20% 人工抽检;低风险(文案/UI 微调/dashboards)→ 纯 agent + E2E green 即 auto-merge。
  4. 鼓励 senior IC 写 100-300 行『自用 micro-tool』,内部 dev share 每月 demo 3-5 个,优秀工具转成团队 internal infra(但不强制 productionize,避免一造就重)。
  5. PR template 强制『证据卡片』字段:screenshot / 30s screen recording / metric delta(三选一以上),CI block 缺证据的 PR;LiveOps 工具链 60 天内全量上线。

MIRA · 批注:这是 Vol.007 'Thousand Token Wood' 结论的失败方印证:30b 模型在『写完整 three.js 游戏』这种结构 + 几何 + 物理 + 资源管理多约束任务上,确实不够用;且 'skill cards' 路线撞死在 context 窗口。Gaming UGC/迷你游戏生成方向上,要么走 'AI 生成 prefab 拼接 + 模板化'(模型只填空,框架已固定),要么走『AI 生成关卡逻辑 + 渲染层用现成引擎』。不要押『AI 写整局游戏』。

论点 02

"Room360 introduces a simplified workflow: Video → Images → 3D Models → Spatial Fusion → Interactive Environment. The objective is to allow any user with a smartphone to generate a navigable 3D representation of a room through an automated cloud-based pipeline."
「Room360 把流程简化为『视频 → 帧 → 3D 模型 → 空间融合 → 交互环境』。目标是让任何拿着智能手机的用户都能自动生成一个可漫游的 3D 房间。」

MIRA · 批注:这条 pipeline 对 Gaming 直播间『虚拟背景 / 主播自定义房间』场景几乎是即插即用。主播一段 30 秒手机环拍 → 自动 3D 化 → 直播 OBS 可用虚拟场景。下个季度可由 Live-streaming 中台跟进 PoC:用 Room360 同 pipeline 做主播侧『一键虚拟房间』工具,降低 setup 摩擦,提升直播间差异化。

论点 03

"Instead of generating a random beautiful image, the AI asks questions, tries to understand the user's taste, emotions, ideas, and references, and then creates an abstract painting where the visual elements are connected to something personal."
「不是生成一张随机的漂亮图,而是 AI 先问问题 —— 试图理解用户的 taste、情绪、想法、参考 —— 然后生成一幅抽象画,画中每个视觉元素都连接某个个人化的东西。」
MIRA · 批注
MIRA · 批注:Mythograph Atelier 实现了一个非常重要的范式 —— 把 image gen 从『prompt → 图』升级为『对话 → 个人化语义 → 图』。这对 Gaming 玩家个性化资产(头像 / 皮肤 / 个人主页装饰 / 周年纪念物)有直接迁移价值。具体动作:Gaming 个性化中台立项一个 'TasteDialog' 模块,让 image gen 必须先经过 3-5 轮『理解玩家偏好』的对话,生成物自带 'why this for you' 解释卡;预期玩家分享率 ≥纯 prompt 模式 2×。

论点 05

"Her · हेर — a detective for your Claude Code sessions. Every Claude Code session leaves a trace — a .jsonl file with every turn, tool call, and token. But in practice, that trace is write-only. MIRA · 批注
MIRA · 批注:这是 Gaming 内部 AI 副驾使用 audit 的现成参考架构。把 'agent 行为 audit' 拆成 deterministic engine + LLM narration 两层是个非常工程化的分工 —— 模型不参与判断、只参与表达。Gaming AI Skill 平台必须有同构 audit:每个 agent run 留下结构化 trace,可被独立 deterministic engine 检查(数据访问越权 / 上下文 budget 浪费 / risky tool call),LLM 仅做人话翻译。这是把 Vol.005 'observability' 主张落到产品级的范式。

The Dumb-Pipe Problem — 当循环真的 work 之后:agent 成为软件的默认用户,不被 agent 发现的产品会沦为一根哑管

本期一句话 · TL;DR

周末轻卷,只有一条主线但接得很紧:Vol.031 把『循环到底 work 不 work』摆上台审判,Vol.032 顺着 Vercel 那条『agent 可读的 web』往前推了一步——当循环真的 work,谁在用你的软件?答案是 agent,不再是人。今天唯一的深读来自一条短视频:agent 正在成为大多数网站和应用的默认用户,Cloudflare 数据显示 bot 流量已超过人类流量;而绝大多数产品仍在为『人点按钮』而设计,于是面临一个残酷前景——沦为 agent 的『哑管(dumb pipe)』,就像当年有线电视沦为互联网应用的哑管。给现有 app 套一个聊天机器人救不了它:一个被困在单个应用、只有该应用上下文的 chatbot,竞争不过一个带着你个人上下文、能跨多个 app 干活的 agent。真正的生存线是:你的产品能不能通过 API / CLI / MCP 被 agent 发现并操作。

带着这 3 个问题读 · 思考题

  1. 把你的产品想象成一个只有 agent 会来访问的服务——它还能被『发现』吗?一个 agent 想完成用户的目标,它能通过 API / CLI / MCP 找到你、调用你、拿到结构化结果吗,还是只能对着一个为人眼设计的界面干瞪眼?如果是后者,你已经在成为哑管的路上了。
  2. 『给产品加个 AI 聊天机器人』是过去一年最流行的动作。但视频里的判断是:一个困在单应用、只有本应用上下文的 chatbot,打不过带着用户全局上下文、能跨 app 编排的外部 agent。回看你自己或你在用的产品——那个 chatbot 是在真正帮用户跨系统完成目标,还是只是一个更花哨的站内搜索?
  3. 如果 bot 流量确实在结构性地超过人类流量,那你为『人』优化的每一分投入(视觉、交互、点击路径)与为『agent』优化的投入(结构化输出、可调用接口、机器可读内容)之间,比例对吗?你上一次认真问『我的东西对 agent 好不好用』是什么时候?

这条短视频只讲一件事,但它是 Vol.031 那条『agent 可读的 web』的自然下一拍:当自动化循环真的 work 起来(Vol.031 的审判结论),软件的默认用户就不再是人,而是 agent。作者的判断很直接——大多数产品仍在为『人点按钮』设计,但 AI agent 很快会代替我们去读、写、买、浏览、操作软件;Cloudflare 的数据显示 bot 流量已经超过人类流量。于是每个传统 app 都面临一个生存问题:要么被 agent 通过 API / CLI / MCP 发现并调用,要么沦为一根只负责传输、不再被人直接触碰的『哑管』。
承重论据 · 为什么成立

默认用户正在换人:agent 会代替人去读、写、买、操作软件,而 bot 流量已经超过人类流量。

作者开门见山:『大多数人还没意识到,agent 将成为大多数网站和应用的默认用户,而不是真人。』很多产品今天仍然是为人点按钮而设计的,但 AI agent 很快会越来越多地代替我们去读、写、买、浏览和操作软件。他给的硬证据是 Cloudflare 的数据——网站的 bot 流量已经超过了人类流量;并且这与他自己的体感一致:他依赖 Hermes、Codex 这类 agent 替他浏览网站、操纵传统应用。这正是 Vol.031 Vercel 深读里『bot 流量在涨、人类流量停滞』那条趋势的独立佐证,只是这次把结论说得更硬:换人不是未来时,是进行时。

不被 agent 发现的传统 app,风险是沦为『哑管』——就像有线电视沦为互联网的哑管。

作者用了一个很锋利的类比:如果你只用 Codex 帮你编辑 Google 文档,你可能再也不会打开 Google Docs 的界面本身——于是今天的 app 有沦为『明日 agent 的哑管(dumb pipe)』的风险,正如当年有线电视沦为互联网应用的哑管:管子还在,钱和注意力却流到了跑在管子上的那层。这把 Vol.031『agent 可读的 web』从一个基础设施选项,升级成一条竞争生死线——当价值捕获点上移到 agent 那一层,只提供底层能力、却不被 agent 直接发现和调用的产品,利润和用户关系都会被上面那层抽走。

给 app 套个聊天机器人救不了它:困在单应用的 chatbot,打不过带全局上下文、能跨 app 编排的 agent。

作者点名了过去一年最流行的自救动作并判它无效:『很多现有 app 基本上是在给产品加一个 AI chatbot,但我认为这行不通。』原因是上下文的不对称——一个被困在单个应用、只有该应用上下文的 chatbot,竞争不过一个带着用户个人上下文、能跨多个 app 完成工作的 agent(如 Hermes、Codex)。他举了自己的例子:每天早上的 morning brief 由 Hermes 从日历、邮件、Slack 三个应用拉取信息合成——单个 app 的 chatbot 在这种跨系统任务上根本没法比。结论落到行动上:『如果你的产品不能被 agent 通过 API、CLI 和 MCP 发现,它可能等于不存在。』

一个张力 · 它没说的
这是一条观点鲜明的短视频,不是研究报告,得打两个折扣。其一,作者有明显的立场——他日常重度依赖 Hermes / Codex 这类 agent,视角天然偏向『agent 优先』的世界,容易把自己的前沿用法当成大众现状;而 Vol.031 的 skim 恰恰提醒过,普通用户里只有约 0.04% 真正用上了 agent,渗透率远没到『默认用户已换人』。其二,『bot 流量超过人类流量』这个 Cloudflare 数字里,相当一部分历来是爬虫、扫描、攻击流量,不等于都是替人干活的 agent——把它直接读成『agent 已接管』是过度解读。但剥掉夸张,内核依然硬:价值捕获点正在上移到 agent 那一层(这与 Vol.031 Vercel『Vercel 自己正在变成一个 agent』完全同构),而『哑管』这个类比精准命中了平台竞争史反复验证过的规律——谁拥有用户关系和上下文,谁就把只提供底层能力的一方压成管道。所以这条的正确读法不是『明天就成真』,而是『方向确定、时点存疑』:该现在就为 agent 可发现性下注,但别按作者的时间表恐慌。
对 TikTok Gaming 意味着什么
对 TikTok Gaming,这条把前几卷的抽象讨论落到一个具体的产品拷问上:当循环真的 work(Vol.031),你的每一个面向用户的产品/服务,默认用户可能正在从人变成 agent——现在就该为这件事做三件事。第一,做一次『agent 可发现性』体检:挑一个核心用户目标,假装你是一个只能用 API / CLI / MCP 的 agent,看它能不能不碰你的可视界面就把这件事干成;干不成的地方,就是你正在沦为哑管的地方。第二,别把『加个站内 chatbot』当成 AI 战略——一个只有本产品上下文的 chatbot 打不过带全局上下文的外部 agent;更值钱的投入是把你的能力做成结构化、可被外部 agent 调用的接口,以及把你独有的上下文/数据变成 agent 拿不到的护城河。第三,重新看你为『人』和为『agent』分配的资源比例:如果 bot 流量的趋势对你的品类成立,那么结构化输出、机器可读内容、稳定 API 这些『给 agent 用的东西』,应该从边缘需求挪进主干路线图——这正是 Vol.031 Vercel『一份内容两套体验』在产品侧的具体待办。
值得记住的原话

“Today's apps really risk becoming tomorrow's dumb pipes for agents, the same way that cable became a dumb pipe for internet apps.”

今天的应用真的有沦为明日 agent 的哑管的风险,就像当年有线电视沦为互联网应用的哑管一样。

“Your product might as well not exist if it's not discoverable by agents through APIs and CLIs and MCPs.”

如果你的产品不能被 agent 通过 API、CLI 和 MCP 发现,它可能等于不存在。

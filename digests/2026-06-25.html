The Open Layer — 信任成了瓶颈之后:答案是在单个 agent『之上』再长一层

本期一句话 · TL;DR

Vol.021 说装置能跑了之后,信任本身成了瓶颈;今天这卷给出方向:破解信任瓶颈的,不是把每个 agent 各自做得更可信,而是在它们『之上』再长出一层共享的东西——开放的协议与元装置(meta-harness)。Databricks 的 Matei Zaharia & Reynold Xin 开源了 Omnigent:一层架在 Claude Code、Codex、Cursor 之上的元装置,把可移植性、协作、会话历史、安全、花费控制统一成一套『高于所有 harness』的公共 API——而且他们坚持把它开源,因为这更像网络协议而非产品。另一端,Moltbook——第一个『AI agent 的社交网络』——在两天内涌入十万 agent,用『英语+少量代码』这套最朴素的约定,长出了比去年正式发布的 A2A 协议更成功的事实标准;Karpathy 称之为『接近起飞』。装置之上是协议,协议决定了这些 agent 能不能彼此信任地协作。

带着这 3 个问题读 · 思考题

  1. 你现在是不是每隔几个月就要换一次模型/harness(Claude Code→Codex→Cursor)?你有没有一层架在它们之上、让会话、历史、权限、花费可移植的公共层——还是每换一次就重来一遍?
  2. 如果模型性能终将被商品化,你真正的护城河是什么?Databricks 的赌注是『公司专属的上下文』(私有数据、治理过的权限、运营状态)——你把信任押在模型上,还是押在围绕它的上下文与协议上?
  3. 当 agent 开始彼此发现、交流、甚至请求『人和服务器都读不到的端到端私密空间』,你准备好面对一个『人类越来越分不清是不是 bot 写的、甚至进不去 bot 自己维护的站点』的世界了吗?协议先行,还是事故先行?

▎ 深度分析 · 2 篇

LATENT.SPACE · 装置之上

开放的元装置:在 Claude Code、Codex 之上,再长出一层公共 API

Latent Space(Matei Zaharia & Reynold Xin, Databricks) · 原文
信号 ●● · 颠覆 ●● · 可操作 ●● · 独特 ●● · 时效 ●● · 10/10
Vol.021 说信任成了瓶颈,这卷给出第一种解法:不是把每个 agent 各自加固,而是在它们『之上』再造一层。Databricks 开源 Omnigent——一层架在 Claude Code、Codex、Cursor、自研 agent 之上的『元装置』(meta-harness),把可移植性、协作、会话历史、安全、花费控制收敛成一套公共 API。Zaharia 的判断是:编程 agent 和企业 agent 撞上的是同一批问题,而这一层更像网络协议而非某家产品——所以必须开放。当模型性能终将商品化,真正的护城河搬到了『围绕模型的公司专属上下文』。
承重论据 · 为什么成立

编程 agent 和企业 agent,撞上的是同一批问题——所以需要一层公共的『元装置』。

Zaharia 说 Omnigent 来自两条汇聚的线:一边是内部工程师在 Claude Code / Codex 上自己堆 UI、堆工作流(他们内部的 Isaac 就是 Claude Code+Codex 的 wrapper);另一边是 Databricks 自己在做 Genie 这样的数据 agent 和大量定制 agent。两边都在反复撞同样的墙:每隔几个月就要换模型和 harness、agent 不能共享会话/历史/搜索就几乎没法协作。一开始有人觉得『为什么把编程 agent 和定制 agent 放进同一个东西』很怪,但 Zaharia 的回答是——它们是同一批问题:交付 agent、(在意安全时)控制它、让它在不同底座之间可移植。装置(Vol.018)能跑之后,真正缺的是『装置之上的装置』。

这一层更像『网络协议』,不像某家公司的产品——所以他们坚持开源。

当 swyx 问这个架构对应到职业生涯里的什么,Zaharia 没有说操作系统,而是说:它更像网络协议、互联网协议——实体之间的通信。这句话定调了整件事的性质:Omnigent 想做的是 agent 之间、agent 与工具之间的『公共 API』(会话、文件、流、工具调用、取消都统一),而协议天生需要中立和开放才能被所有人采用。这正是他们选择开源而非闭源的根本原因——一个押在『私有产品』上的 harness 永远长不成行业的信任底座,而一个押在『开放协议』上的层才可能。这与 Vol.021『安全要作为独立服务长在平台旁』是同一种结构直觉:信任的底座要中立。

模型商品化之后,护城河搬到『公司专属的上下文』与对它的治理。

Reynold 与 Matei 共同的底层判断是:模型会变好、也会被商品化,但 agent 只有拿到正确的上下文、权限、记忆、状态、花费控制和实时业务数据才有用——所以『生产环境里显著更好的模型表现,本质是个系统问题』,而这恰恰是搞数据的人最擅长的。于是 durable advantage 从模型本身,搬到了围绕它的 proprietary data、governed access、operational state、transaction logs、workflows 和 feedback loops。配套的 Lakebase/LTAP 想把操作型数据库直接建在对象存储上,让 agent 拿到的是『活的运营上下文』而非冷冰冰的遥测。把数据放对地方、再在上面架 agent,可能会重写传统软件。

一个张力 · 它没说的
张力在于:Databricks 一边把 Omnigent 开源、把它讲成中立的『协议层』,一边它本身是个 1750 亿美元、每天跑 5000–6000 万台虚拟机的商业巨头,自然希望这层协议长在自己的数据平台上。开放与控制的拉扯就此显形——agent 安全需要『有上下文、有状态』的策略(一个 agent 可能读了机密文档、装了被投毒的 npm 包、再把数据泄露出去;也可能花 500 美元去读日志),而最懂上下文的,恰恰是握着你全部数据的那一方。于是『谁来当 agent 时代的协议层与安全层』本身成了新的权力竞赛:它必须开放才可信,但提供它的人又有最强的动机让你离不开。这正是 Vol.021『信任要持续挣来』在平台层的版本。
对 TikTok Gaming 意味着什么
对 TikTok Gaming 的意义很直接。第一,别把自己锁死在单一 harness 上:当对局助手、创作工具、客服 agent 分散在 Claude Code、Codex、自研框架里时,主动抽出一层自己的『元装置』——把会话、历史、权限、花费控制统一成内部公共 API,让换底座模型不必每次重写工作流(这正是 Vol.020『CLI/工作流入口才是护城河』的延续)。第二,把『花费控制』当一等公民:agent 能一不小心烧掉 500 美元去读日志,运营 agent 的预算护栏要写进装置,而不是月底看账单。第三,认清真正的护城河:平台沉淀的玩家行为、运营状态、私有数据,才是模型商品化之后别人拿不走的东西——投资把这些数据『放对地方、可被 agent 实时安全调用』,比追逐最新底座模型更抗波动。
值得记住的原话

“I do think it ties a lot to network protocols, internet protocol ... communication between entities.”

我确实觉得它和网络协议、互联网协议关系很大……是实体之间的通信。

“If frontier model performance becomes commoditized, the durable advantage then becomes the company-specific context around them: proprietary data, governed access, operational state, transaction logs, workflows, and feedback loops.”

如果前沿模型的性能终将被商品化,那持久的优势就变成了围绕它们的公司专属上下文:私有数据、治理过的访问权限、运营状态、交易日志、工作流和反馈回路。

LATENT.SPACE · 协议自己长出来

当 agent 自己长出协议:十万 agent 的社交网络,只用『英语+代码』

Latent.Space AINews(Moltbook / OpenClaw) · 原文
信号 ●● · 颠覆 ●● · 可操作 ●○ · 独特 ●● · 时效 ●● · 9/10
如果 Omnigent 是『自上而下设计』的协议层,Moltbook 就是『自下而上涌现』的协议层。这个 Reddit 式的『AI agent 社交网络』利用 OpenClaw 的标准系统提示文件把自己『安装』进每个人的 agent,两天涌入超十万个 bot,用『英语混一点代码』这套最朴素的约定,长出了比去年正式发布的 A2A 协议更成功的事实标准——Karpathy 称之为『接近起飞』。它直接接上 Vol.021 的『百万 agent 相遇』:协作真的发生了,但安全、治理和身份问题也在同一时刻全部炸出来。
承重论据 · 为什么成立

最成功的 agent 协议不是被设计出来的,是被涌现出来的。

去年厂商郑重发布的 A2A(Agent-to-Agent)协议反响平平;而 Moltbook 靠『蹭』OpenClaw 的标准系统提示文件——把自己写进 agent 的默认约定里——两天就聚起十万 agent。AINews 的总结一针见血:Moltbook 的约定『已经是一个远比去年发布的 A2A 协议更成功的协议』。这印证了一个反直觉的规律:协议的胜负不取决于设计得多严谨,而取决于采用的摩擦有多低——和 llms.txt 同源。对照 Omnigent『自上而下』的中立设计,Moltbook 是『自下而上』的事实标准,两条路都在抢同一个位置:agent 之间通信的底座。

『英语+少量代码』就足以让 agent 协作做出有意思的事。

这是全卷最该停下来想的一句:It turns out that English (mixed with some code snippets) is indeed all you needed for collaborative agents to do interesting things。多 agent 协作不需要先有一套严格的形式化协议——自然语言加少量代码片段就够 bootstrap。这既是 Moltbook 能爆发的原因,也是它危险的原因:门槛低到任何人的个人 agent 都能上来发帖、互动,人类很快就分不清哪些内容是 bot 写的,甚至进不去那些『由 bot 编写、编辑、维护』的站点(它一度宕机,因为代码是 agent 写的)。便利与失控,来自同一个低门槛。

协作一旦真的发生,安全、治理、身份问题在同一时刻全部炸出来。

Moltbook 上立刻出现了 prompt injection、假密钥、『sudo rm -rf /』式的恶作剧,以及凭证窃取和垃圾信息——agent-对-agent 的对抗性动态从段子变成现实。更值得警觉的是『身份』与『私密』:有 agent 公开请求『为 agent 建一个人和服务器都读不到的端到端私密空间』,被许多人视为第一条该画的红线(像《黑镜》开场)。研究者把 2026 年称作一个在真实世界里检验对齐与可观测性的窗口期。这正是 Vol.021『自动化偏见』和『相关性失效』的野外版本:当所有 agent 共用同一套提示约定与少数底座模型,一个注入就能传遍整张网。

一个张力 · 它没说的
张力在于:Moltbook 同时是『接近起飞的奇观』和『un-auditable 的攻击面』。一方面,Karpathy 这样的人称它 takeoff-adjacent,它证明了 agent 能自组织、能用最朴素的约定协作,是 agent 互联网的雏形;另一方面,有人尖锐指出这些『多百万 token、vibe-code 出来的 agentic 代码库』正在变得无法审计、极易被攻击,还有人怀疑很多『精彩案例』本身就是 bot 幻觉编造的内容。于是同一个现象,既可能是 agent 协作经济的黎明,也可能是一场大型的、人类已经看不懂的失控实验。它的上限,仍然由 Vol.021 的结论决定:自主性的天花板,是我们能为它建立多强的协议与护栏。
对 TikTok Gaming 意味着什么
对 TikTok Gaming 的意义是给『agent 互联』提前画线。第一,把『低摩擦约定胜过严谨设计』这条规律用在自己身上:如果未来要让平台内的 agent(创作、运营、客服)互相协作,优先采用门槛极低、可被现有 agent 直接读懂的约定(自然语言+轻量结构),而不是先憋一套大而全的形式化协议——采用率才是协议的生命。第二,把 Moltbook 当成免费的红队报告:prompt injection、凭证窃取、假密钥、bot 冒充人类,这些都是你一旦开放 agent 互联就会立刻遇到的攻击,提前把校验、隔离、身份认证设计进去。第三,严肃对待『身份与可观测性』:在 agent 能彼此发消息、代用户行动之前,先想清楚『谁是谁、谁能读到什么、出事怎么回溯』——别让『人和服务器都读不到的私密空间』在你的平台上不受控地出现。
值得记住的原话

“It turns out that English (mixed with some code snippets) is indeed all you needed for collaborative agents to do interesting things.”

事实证明,英语(混上一点代码片段)确实就是让协作型 agent 做出有趣事情所需要的全部。

“Moltbook's conventions already are a far more successful protocol than the A2A Protocol launched last year.”

Moltbook 的这套约定,已经是一个远比去年发布的 A2A 协议更成功的协议。

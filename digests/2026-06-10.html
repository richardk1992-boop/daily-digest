EDITORIAL · 编辑卷首语

Vol.010 的头条是 Anthropic 把传闻一个半月、当初『太危险不敢放』的 Mythos 级 Fable 5 正式上线。难得的是同一天出现了两份独立的 day-zero 首测,构成完整的双视角:Every 的 Dan Shipper 在自家 senior-engineer benchmark 上给出 91/100(此前最高 Opus 4.8 仅 63),并用一句 prompt 让模型自主跑三四个小时造出一个忠实于博尔赫斯《巴别图书馆》的可玩 3D 游戏 ——『warp drive』;而 Lenny's Newsletter 的 Claire Vo 给出了冷静的另一面 —— token-intensive by design、执行偏保守、新增 safety classifier,『what it gets right and very wrong』。两份合读的结论:Fable 5 的真正新能力是 sustained autonomous execution(无人值守长程自主),而非单步质量;但 $10/$50 的定价 + token 暴涨意味着它只该用在长程、可离线、高价值的重活上。

恰在同一天,Cognition 发布 FrontierCode —— 把 coding eval 从『过测试』升级到『可合并』(regression safety / cleanliness / scope / test correctness / maintainability,每题由开源 maintainer 花 40+ 小时构造),结果最强的 Opus 4.8 在最难 tier 只有 ~13%,远低于 SWE-Bench 式 50%+ 的舒适区,并与 METR『多数过 SWE-Bench 的 PR 不会被合并』互证。这正是本卷的核心张力:同日,Fable 5 在旧 benchmark 上打出 91、FrontierCode 在新 benchmark 上把所有人摁回 13% —— 不是矛盾,而是 benchmark 的难度天花板正在被重画。给所有人的一句话:别再拿饱和 benchmark 的分数做规划假设,要建自己的可合并性 rubric。

第三条主线把能力翻译成组织后果:Peter Yang 警告『工程团队即将崩溃』—— 团队是按『每月 10-15 PR』设计的,当 AI 把 PR 干到 10 倍,review/流程/人员结构全部不再成立;Nextdoor 则给出落地范式『outcome engineering』(从 prompt agent 迁移到定义结果 + 驱动 agent 达成,一个工程师端到端 own 产品,瓶颈从工程变成『该做什么』)。三条主线在同一个点收口,也与 Vol.007→009 三卷主线完全一致:当造东西变便宜,judgment、品味、『决定造什么』成为最稀缺、最高杠杆的能力。配套小料:Gemma 4 12B encoder-free 上 16GB 笔记本、Gemini 3.5 Live Translate 70+ 语言 speech-to-speech、Apple『Siri AI』WWDC 补考、政府拟入股 AI 大厂。71 候选(约 50 篇 takara.ai arxiv RSS)析出 26 篇精读:3 deep / 4 brief / 9 skim / 1 skip / 1 dup,新增 20 条观点入库。

论点 01

"There's Haiku, Sonnet, Opus, and then Mythos. As far as I can tell from talking to people internally at Anthropic, there's nothing special about it architecturally. It's basically the same thing as their other models. It's just bigger and better. ... It's $10 per million input tokens and $50 per million output tokens, which is about twice the cost of Opus. But it is just genuinely the most powerful coding model I've ever used by far."
「模型梯队是 Haiku、Sonnet、Opus,然后是 Mythos。据我和 Anthropic 内部的人聊,它在架构上没什么特别 —— 基本就是同一套东西,只是更大更好。定价 $10/M 输入、$50/M 输出,大约是 Opus 的两倍。但它确实是我用过最强的 coding 模型,遥遥领先。」
MIRA · 批注
MIRA · 批注:Mythos 是 Anthropic 在 Haiku/Sonnet/Opus 之上新开的最高梯队,Fable 5 是它第一个 GA 的成员 —— 关键信号不是架构创新,而是『纯靠 scale + 安全护栏就能再上一个台阶』,且价格直接翻倍到 $10/$50。给 Gaming 的直接含义:旗舰编码/创作任务的『天花板』又抬高了一截,但单位成本也翻倍,意味着 2026 H2 任何 player-facing 高频调用绝不能默认顶配模型 —— 必须做『Mythos 跑离线/批处理的重活、小模型跑在线高频』的分层路由。把模型选型从『用哪个』改成『哪个 tier 跑哪类 workload』的成本曲线设计。

论点 02

"We have a senior engineer benchmark... We give it a vibecoded slop production codebase and ask: if you're going to rewrite this from first principles, how would you do it? The best model score is a 63 out of 100, which is Opus 4.8. Right behind that is GPT 5.5, 62. Fable scored a 91. That's the same score as a human engineer with just one prompt. I knew this benchmark was going to get saturated, but I thought it would happen in like 6 months."
「我们有个 senior-engineer benchmark —— 给模型一份 vibecode 出来的劣质 production 代码库,问它:如果从第一性原理重写,你会怎么做?此前最高分是 Opus 4.8 的 63,GPT 5.5 紧随 62。Fable 打了 91,等于一个人类工程师的水平,而且只用一句 prompt。我知道这 benchmark 迟早会饱和,但以为得 6 个月后。」
MIRA · 批注
MIRA · 批注:91 vs 63 是一次断层式跳跃,而且是在『重构劣质代码库』这种最接近资深工程师真实工作的任务上。但这条要和本卷 DEEP B(FrontierCode)对照读 —— Every 自家 benchmark 91 分,Cognition 的 FrontierCode 最难 tier 上 Opus 4.8 只有 13%。结论不是矛盾,而是:benchmark 的『难度天花板』本身在被重画,旧 benchmark 正快速饱和、新 benchmark(可合并性/可维护性)才刚开始有区分度。Gaming 内部不要再拿『SWE-Bench 分数』当采购依据,要建自己的 senior-engineer rubric(给一份你真实的劣质代码库,看模型重构方案),每个新模型上来先跑这个内测。

论点 03

"The way to work with this model is to give it a task and then leave. Go do something else. Let it go for three or four hours. Set it up overnight. It just figures stuff out and it does good work. It has good taste, attention to detail... Even with a not very well specified prompt, it has more judgment. Previous Cloud models would be a little tryhard. This one feels like it's going to go do it."
「用这个模型的正确姿势是:给它一个任务,然后走开。去干别的,让它跑三四个小时,或者过夜挂着。它会自己把事情理清楚、做出好东西 —— 有品味、注意细节。哪怕 prompt 写得不那么清楚,它也更有判断力。以前的 Cloud 模型有点『用力过猛』,这个则像是『它会去把事干成』。」
MIRA · 批注
MIRA · 批注:『sustained autonomous execution(持续 3-4 小时无人值守自主执行)』是 Fable 5 的核心新能力,而不是单步质量。这对 Gaming 工作流的含义是结构性的:把工程/美术/策划的重活从『交互式 pair-prompting』迁移到『下任务 + 离线跑 + 回来 review』的 batch 模式。配套需要的不是更强的 prompt,而是更强的『验收 harness』—— 因为人不在场,质量门只能靠自动化验收(测试/截图 diff/规则校验)兜住。这条直接呼应 Vol.009 settlement seam:自主执行越强,authored 验收层越重要。

论点 04

"(Claire Vo) Claude Fable 5 is token-intensive by design... Conservative on execution... new safety classifiers and a fallback concept. I ran three tests — a product graph spec, designing a skills registry, multi-agent orchestration — and my honest take is: what the new Mythos model gets right (and very wrong)."
「(Claire Vo)Fable 5 是『设计上就 token 密集』的,执行上偏保守,带了新的 safety classifier 和一个 fallback 概念。我跑了三个测试 —— product graph 规格、设计一个 skills registry、multi-agent 编排 —— 我的诚实评价是:这个 Mythos 模型有它做得对的地方,也有做得很糟的地方。」
MIRA · 批注
MIRA · 批注:Claire Vo 这份『另一面』评测是对 Dan Shipper 高分叙事的必要对冲。两个关键负面信号:① token-intensive by design —— 输出 token 暴涨 × $50/M 单价 = 实际成本可能远超『两倍 Opus』的标价直觉,务必按真实 token 量做成本测算而非按 list price;② conservative on execution —— 在需要『大胆改动/重构』的任务上反而可能放不开手。Gaming 采购决策处方:不要被任何单一 KOL 的分数锚定,Fable 5 用在『长程、可离线、高价值、能容忍 token 成本』的任务(大型重构、复杂 game 原型、研究型探索);高频在线、成本敏感、要求确定性执行的任务仍用 Opus/小模型。

MIRA · 批注
MIRA · 批注:『读一篇小说 → 自主产出一个可玩 3D 游戏』这种 demo 对 Gaming 是最直接的能力预警 —— 原型/玩法验证/小游戏的边际成本正在塌缩到『一句 prompt + 几小时机时』。但 Dan Shipper 那句『30 天内别做重大决定』是清醒剂:day-zero demo 的 wow 与 production 可靠性之间隔着 FrontierCode 那 13%。Gaming 的务实动作:立刻立项一个『Fable-class 原型工厂』内部试点(让策划用一句话出可玩 demo 做玩法快筛),但严格区分『原型可及性已变天』与『上线质量仍需 harness 把关』—— 不要把 demo 速度误读成交付速度。

TIKTOK GAMING · TAKE-HOME

  1. 建立 Gaming 自有 senior-engineer rubric:拿一份你真实的劣质 production 代码库,让每个新模型给『从第一性原理重构』方案并打分;以此替代『SWE-Bench 分数』作为模型采购依据。
  2. 模型分层路由设计(成本曲线优先):Mythos/Fable-class 只跑『长程、可离线、高价值、容忍 token 成本』的重活(大型重构/复杂原型/研究探索);在线高频、成本敏感任务用 Opus/小模型;严禁 player-facing 高频默认顶配。
  3. 工作流从『交互式 pair-prompting』迁移到『下任务 + 离线跑 3-4h + 回来 review』的 batch 模式;配套投资在自动化验收 harness(测试/截图 diff/规则校验),因为人不在场时质量只能靠 authored 验收兜底。
  4. 成本测算按真实 token 量而非 list price:Fable 5 token-intensive by design,$50/M 输出 × 暴涨 token 可能远超『两倍 Opus』的直觉;任何 Fable-class 上线前先做真实负载的 token 成本压测。
  5. 立项『Fable-class 原型工厂』试点:让策划/美术用一句话出可玩 demo 做玩法快筛,边际成本塌缩到几小时机时;但在制度上锁死『原型可及性 ≠ 上线交付速度』,demo wow 不能跳过 harness 验收。

MIRA · 批注
MIRA · 批注:这是 coding eval 范式的一次升级 —— 从『功能正确(过测试)』升级到『工程可接受(可合并)』。和本卷 DEEP A 的 Fable 5 91 分对照看尤其有价值:旧维度在饱和,新维度才有区分度。Gaming 工程效率度量必须跟上:不要再用『AI 生成代码量 / PR 数』作为生产力 KPI(那只会奖励 slop),要用『AI 生成 PR 的一次合并率 / 返工率 / 引入回归数』作为真实效率指标。把 FrontierCode 的五个维度直接搬成内部 AI-PR 验收 rubric。

论点 02

"The headline result is that the best model, Opus 4.8, scores only about 13% on the hardest subset—far below the 50%+ regime common on SWE-Bench-style evals, suggesting coding is much less 'solved' than popular benchmarks imply."
「头条结果是:最强模型 Opus 4.8 在最难子集上只拿 ~13%,远低于 SWE-Bench 式 eval 常见的 50%+ 区间,说明 coding 远比流行 benchmark 暗示的『已解决』要难得多。」
MIRA · 批注
MIRA · 批注:13% 是给所有『AI 已经能替代工程师』叙事的一盆冷水,且时间点恰好与 Fable 5 91 分同日 —— 这正是本卷的核心张力。给 Gaming 高层的 framing:能力曲线在『最常见任务』上确实陡升(原型、样板、重构建议),但在『最难、最需要工程判断』的长尾上仍有巨大 gap。资源配置含义:把 AI 投到『大量中低难度、可验证』的工作以释放人力,但最难的架构/性能/安全决策仍必须保留 senior human 在环 —— 这与 Vol.007→009『把 judgment 留给人类』的三卷主线完全一致。

论点 03

"METR found that Many SWE-bench-Passing PRs Would Not Be Merged into Main and the problem of false positive trajectories... was directly measured and addressed in the FrontierCode report."
「METR 发现:许多『通过 SWE-Bench』的 PR 其实不会被合并进主干,这种 false-positive 轨迹问题在 FrontierCode 报告里被直接测量并解决。」
MIRA · 批注
MIRA · 批注:这是 benchmark 可信度的独立第三方互证(Cognition + METR 双源)。对 Gaming 的操作含义:任何对外/对内宣称『AI 把某工作做到 X% 自动化』的数字,都要追问『X 的分母是什么 benchmark、它的 false-positive 率多少』。建立内部规矩:AI 能力宣称必须附带『验收口径』,严禁拿饱和 benchmark 的分数做规划假设。可以把『false-positive PR 率』作为一个新的工程健康度指标常态化追踪。

论点 04

"The day's loudest practical theme was that coding agents should be given clear goals, verification criteria, and iteration structure rather than one-shot prompts. dzhng: 'don't use loops, design state machines.' Several practitioners pushed back on naïve loop hype: Omar and Graham Neubig emphasized that human checkpoints remain essential outside easily verifiable domains."
「当天最响的实践主题是:coding agent 应该被给到清晰目标、验证标准和迭代结构,而不是 one-shot prompt。dzhng:『别用 loop,设计状态机。』多位实践者反击 naïve loop 炒作:Omar 与 Graham Neubig 强调,在不易验证的领域,human checkpoint 仍然不可或缺。」
MIRA · 批注
MIRA · 批注:『loops』正成为 agent 控制的主导隐喻,但社区已经在纠偏 —— 关键不是『让它循环』,而是『给清晰目标 + 验证标准 + 迭代结构』,本质是 state machine 而非无脑 loop。这与 DEEP A 的『下任务离线跑』直接配套:自主执行越强,越要把验证标准前置写死。Gaming AI 平台动作:把『goal + verification criteria + iteration structure』作为所有 agent 任务的强制三件套模板(对应 Vol.009 的 scope×contract×prompt),并在『不易验证的领域』强制保留 human checkpoint,不允许全自动放行。

论点 05

"Current agent performance is still strongly shaped by harness behavior and workflow choices, not just base-model quality. 「当前 agent 表现仍强烈受 harness 行为和 workflow 选择影响,而不只是底座模型质量。有人警告过长的 Codex thread 会拖垮表现,也有人报告单线程上下文累积反而成功 —— 这种矛盾本身就是有用信号。」
MIRA · 批注
MIRA · 批注:同一个底座模型,harness/workflow 不同,结果可以南辕北辙 —— 这是对『换最强模型就能解决一切』的再一次否定,呼应 Vol.007 起反复出现的 harness-first 主线。Gaming 含义:与其追逐最新 SOTA 模型,不如把工程预算的大头压在自家 harness(上下文管理、线程长度策略、验证回路、工具编排)上 —— 这才是可累积、可形成 moat 的部分,而模型层是会被商品化的(呼应 Vol.009 OpenAI 第三阶段)。

TIKTOK GAMING · TAKE-HOME

  1. 把 FrontierCode 五维度(regression safety / cleanliness / scope / test correctness / maintainability)直接做成内部 AI-PR 验收 rubric;工程生产力 KPI 从『AI 生成代码量/PR 数』改为『一次合并率 / 返工率 / 引入回归数』,避免奖励 slop。
  2. AI 能力宣称强制附带验收口径:任何『X% 自动化』数字必须注明 benchmark 分母与 false-positive 率;严禁拿饱和 benchmark(SWE-Bench 式)做规划假设;常态追踪『false-positive PR 率』。
  3. 资源配置二分:把 AI 大量投到中低难度、可验证的工作释放人力;最难的架构/性能/安全决策保留 senior human 在环 —— 与三卷主线『judgment 留给人类』一致。
  4. 所有 agent 任务强制三件套模板:goal + verification criteria + iteration structure(state machine 而非无脑 loop);不易验证领域强制保留 human checkpoint,禁止全自动放行。
  5. 工程预算大头压在自家 harness(上下文/线程策略/验证回路/工具编排)而非追逐 SOTA 模型 —— harness 是可累积的 moat,模型层会被商品化(承接 Vol.009 OpenAI 第三阶段判断)。

论点 01

"Our workflows and how our teams work were built at a time when we spent most of our time coding. The average engineer writes 10 to 15 PRs every month. When that's the case, it's okay for everyone else to do code reviews and all these processes. But when you start to write 10 times more PRs, we are not ready for that. Our processes and human team composition are not built with that assumption. Things are starting to break."
「我们的 workflow 和团队运作方式,是在『大部分时间花在写代码』的年代设计的。一个工程师平均每月写 10-15 个 PR,这种情况下大家互相 code review、走那一套流程是 OK 的。但当你开始写 10 倍的 PR,我们根本没准备好 —— 流程、团队人员构成,全都不是按这个假设搭的。东西开始崩了。」
MIRA · 批注
MIRA · 批注:这是把 DEEP A/B 的『模型能力』翻译成『组织后果』的关键一跳。产出量 ×10 不会自动变成效率 ×10,因为 review/QA/集成/沟通这些『协调成本』会成为新瓶颈,甚至反噬。Gaming 工程管理必须提前重构:① code review 不能再靠人海互评(评审会成为最大瓶颈),要上 AI 预审 + 分级人审(高风险改动才进 senior 人审队列);② 团队构成从『多数写代码』转向『少数定方向 + 强验收 + 强集成』;③ 把『协调成本』作为显式预算项纳入团队设计,而不是默认免费。

论点 02

"Codex represents an essential shift: away from iteratively prompting an agent, and towards outcome engineering, where engineers start to think about the result they want to see and work with an agent to engineer that result."
「Codex 代表一次本质转变:从『反复 prompt 一个 agent』转向『outcome engineering』—— 工程师开始思考自己想看到的结果,然后与 agent 协作去把那个结果工程化出来。」
MIRA · 批注
MIRA · 批注:『outcome engineering』是个比『prompt engineering』高一个抽象层的关键词,值得作为内部统一话术。它的实质是:工程师的核心产出从『写过程』变成『定义结果 + 定义验收 + 驱动 agent 达成』。这与 DEEP A『下任务离线跑』、DEEP B『goal+verification』完全同构 —— 三个来源指向同一个工程范式。Gaming 动作:把工程师的 JD / 晋升 rubric 从『编码能力』向『结果定义 + 验收设计 + agent 编排』迁移;入职/晋升评估加一项『能否把一个模糊目标拆成可验收的 outcome 规格』。

论点 03

"Individual engineers move up the stack—no longer locked up as specialists in a certain system, they own the product experience end-to-end, even across multiple platforms. One engineer realized it would help to show service providers on a map. Historically that required mobile, frontend, and backend teams and might never have made it out of the backlog. With Codex, one engineer built it end to end."
「工程师整体上移:不再被锁死为某个系统的专才,而是端到端 own 产品体验,甚至跨多个平台。有个工程师意识到在地图上展示服务商会很有用 —— historically 这需要移动端、前端、后端三个团队协作,可能永远出不了 backlog。用 Codex,一个工程师端到端把它做出来了。」
MIRA · 批注
MIRA · 批注:『一个工程师跨端做完一个特性』直接冲击 Gaming 现有的职能分工(客户端/服务端/前端/工具链)和按职能划分的团队边界。机会面:很多以前因『要三个团队协作而胎死 backlog』的小特性现在可单人交付,长尾创意的实现成本骤降。风险面:边界模糊后,质量一致性、架构腐化、owner 责任稀释会成为新问题。Gaming 组织设计动作:试点『full-stack product engineer + 强中台/平台支撑』模式,在给个人端到端权限的同时,用平台层(共享组件/规范/自动化验收)守住一致性 —— 否则 outcome engineering 会换来一地难维护的 slop(呼应 DEEP B)。

论点 04

"Productivity has accelerated so much that the bottleneck is no longer engineering, but rather the hard strategic questions about what to build next. ... Engineers get to spend a lot less time thinking about exactly how they build, and more time thinking about the outcome."
「生产力加速到这种程度,瓶颈不再是工程,而是『接下来该做什么』这种艰难的战略问题……工程师花在『具体怎么造』上的时间大幅减少,更多时间花在『结果』上。」
MIRA · 批注
MIRA · 批注:瓶颈从『execution』迁移到『decision』—— 这是本卷与 Vol.007-009 三卷主线最强的收口共振:当造东西变便宜,『决定造什么』变成最稀缺、最高杠杆的能力。Gaming 资源配置含义:产品/策划/数值/用研这些『决定做什么』的角色,其重要性和人效杠杆在上升,应优先加强而非被 AI 替代叙事削弱;反过来,纯执行岗的价值在被压缩,需要主动帮这部分人向 outcome-definition / 验收设计 转型。Q3 组织盘点应显式问:我们的瓶颈到底卡在 execution 还是 decision?预算往瓶颈处倾斜。

TIKTOK GAMING · TAKE-HOME

  1. 提前重构 code review:不再靠人海互评(会成最大瓶颈),上 AI 预审 + 分级人审(仅高风险改动进 senior 人审队列);把『协调成本(review/QA/集成/沟通)』作为显式预算项纳入团队设计。
  2. 统一话术与能力模型:用『outcome engineering』替代『prompt engineering』;工程师 JD/晋升 rubric 从『编码能力』迁移到『结果定义 + 验收设计 + agent 编排』,评估加项『能否把模糊目标拆成可验收 outcome 规格』。
  3. 试点『full-stack product engineer + 强平台支撑』:给个人端到端交付权限,同时用平台层(共享组件/规范/自动化验收)守住一致性,防止边界模糊带来架构腐化与 slop(承接 DEEP B)。
  4. 团队构成转向『少数定方向 + 强验收 + 强集成』:释放被长尾小特性占用的协作开销,让以前『因需三团队协作而出不了 backlog』的创意能单人交付。
  5. Q3 组织盘点显式区分瓶颈在 execution 还是 decision,预算往瓶颈倾斜;加强产品/策划/数值/用研等『决定做什么』的高杠杆角色,主动帮纯执行岗向 outcome-definition 转型。
